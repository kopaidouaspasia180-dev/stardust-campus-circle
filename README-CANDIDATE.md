# 两小时全产品交付挑战

这是一个正在开发中的校园生态微信小程序半成品，包含微信小程序前端、H5、后端 API、PostgreSQL 数据库和运营管理后台。

你的任务不是单独优化某个页面或功能，而是在两小时内对整个项目进行检查、修改和完善，让它尽可能接近一套视觉统一、功能完整、逻辑合理、能够正常运行和继续交付的成熟产品。

项目仅用于技术面试和能力评估，不是清华大学官方项目，请勿公开发布、商业使用或接入真实用户数据。

## 一、试做时间

本次试做限时两小时，从收到并开始查看源码时计时。

两小时内不要求从零重写整个项目，但最终成果必须体现对全产品的整体优化，不能只修改一个独立页面或单一功能。请根据自己的判断确定修改优先级，在有限时间内尽可能提高整个项目的完成度和交付质量。

## 二、项目范围

项目目前包含首页、校园服务、校园圈、校园榜单、个人中心、课表与日程、校园商店、二手闲置、校园跑腿、学生兼职、校园活动、失物招领、匿名匹配、消息与聊天、后端 API、PostgreSQL 数据库和运营管理后台。

你需要从整体产品角度检查这些页面和功能之间是否统一、连贯，并根据实际情况进行修改。

## 三、试做目标

### 1. 整体视觉统一

至少检查首页、校园服务、校园圈、榜单和“我的”五个底部主页面，重点关注：

- 整体配色、字号和信息密度是否适合手机阅读。
- 页面是否拥挤或留白不合理。
- 卡片、按钮、图标和圆角风格是否一致。
- 底部导航栏是否正常显示。
- 页面是否存在溢出、遮挡、错位或点击区域过小。
- 加载、空数据、失败和禁用状态是否清楚。

### 2. 核心功能连贯

至少检查：

- 首页信息是否能够正常展示。
- 校园服务入口是否能够直接进入对应页面。
- 校园圈是否能够浏览内容并进入发布流程。
- 二手、跑腿、兼职和失物招领是否能够进入沟通流程。
- 榜单是否能够浏览、点赞或进入投稿流程。
- “我的”页面是否能够展示用户相关数据。
- 运营后台是否能够查看或管理前端产生的数据。

不得只制作静态页面，也不得使用假成功提示冒充下单、支付、聊天、审核或数据保存成功。

### 3. 前后端逻辑对应

请检查前端功能是否有对应的后端接口和数据逻辑，包括：

- 页面数据是否来自真实接口。
- 创建、修改、取消和状态变化是否能够保存。
- 用户是否只能操作自己的数据。
- 不同校区的数据是否正确隔离。
- 运营后台是否能够管理前端产生的内容。
- 接口失败时前端是否提供正确提示。
- 空数据时是否展示真实空状态，而不是自动填充虚假数据。

如果微信登录、支付、内容审核或第三方数据接口因为缺少外部凭据无法完成，应展示明确的“尚未配置”状态，不得伪造成功。

### 4. 运营后台可用

请检查运营后台是否能够正常进入，并重点关注首页公告和状态维护、校园圈内容审核、商品和订单、校园活动、快递信息、兼职发布、用户与校区、举报和审计记录。运营后台和小程序前端应使用同一套真实数据逻辑。

### 5. 工程可以交付

最终项目应尽可能满足：

- TypeScript 检查通过。
- 后端能够正常启动。
- 微信小程序和 H5 能够正常构建。
- 数据库迁移能够执行。
- 代码结构清楚，避免大量重复代码。
- 不提交真实密钥、个人数据、数据库备份和上传文件。
- 不使用无法说明来源的第三方代码。

## 四、评分细则

总分为 100 分。

| 评分项目 | 分值 | 评分重点 |
|---|---:|---|
| 整体产品判断 | 15 分 | 是否能够快速发现影响产品交付的主要问题，修改优先级是否合理 |
| 全局 UI 与交互 | 20 分 | 五个主页面和功能页面是否统一、舒适、清晰，导航和状态反馈是否完善 |
| 核心功能完整度 | 20 分 | 首页、服务、社区、榜单、个人中心和沟通流程是否能够连贯使用 |
| 前端、后端与后台一致性 | 20 分 | 前端操作、API、数据库和运营后台是否形成真实业务闭环 |
| 工程质量与稳定性 | 15 分 | 代码结构、类型、数据隔离、错误处理、数据库迁移和安全性 |
| 最终交付完成度 | 10 分 | 项目是否能够安装、构建和运行，修改介绍是否清楚 |

## 五、评分限制

- 只优化一个页面或单一功能：总分最高 55 分。
- 没有检查五个底部主页面：总分最高 65 分。
- 只修改前端，不检查后端和运营后台：总分最高 65 分。
- 使用大量静态假数据伪造完整功能：总分最高 40 分。
- 项目因为本次修改无法构建或运行：总分最高 50 分。
- 只提交说明、不提交修改后的源码：本次试做无效。
- 提交真实密钥、个人数据或擅自公开部署：本次试做无效。
- 明显复制第三方代码但未说明来源：工程质量部分不得分。

## 六、需要提交的内容

两小时结束后只需要提交以下两项：

### 1. 修改后的完整源代码

源代码应当能够正常安装、构建和运行。请不要提交 `node_modules`、`dist`、`dist-h5`、`.git`、`.env`、真实密钥、数据库备份、上传文件或日志文件。

### 2. 简单的修改介绍

请用一份简短的 Markdown 或文本文件说明：

- 你认为原项目主要存在哪些问题。
- 你对整个产品做了哪些修改。
- 哪些问题因为两小时时间限制没有完成。
- 项目的安装和运行方式。
- 是否使用了 AI、开源代码或第三方组件。

不强制提交截图、录屏、测试报告或单独的产品检查表。

## 七、最终说明

两小时结束时应提交当前成果，不需要为了补齐所有功能而延迟。

我们不会单纯比较修改代码的数量，而是重点考察候选人能否在有限时间内快速理解已有项目、发现影响交付的关键问题、合理安排修改优先级、统一整个产品的视觉与交互、补齐前端与后端之间的业务逻辑，并把半成品整理成更成熟、更可信、更接近交付状态的产品。

## 八、本地运行参考

```bash
npm ci
npm --prefix server ci
npm run typecheck
npm run build:weapp
npm run build:h5
```

后端需要 PostgreSQL。复制 `server/.env.example` 为仅供本机使用的环境配置后执行：

```bash
DATABASE_URL=postgresql://... npm --prefix server run migrate
DATABASE_URL=postgresql://... npm --prefix server start
```

`project.config.json` 使用游客 AppID，只适合本地编译。正式预览需要候选人自己的测试 AppID，禁止使用真实生产密钥。
