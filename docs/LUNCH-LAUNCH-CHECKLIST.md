# 小饭桌上线检查单

## 已在代码中完成

- 唐山学院、唐山师范学院及校区选择；客户端把高校和校区一起发送到服务端。
- 校区级商家、商品、订单和配送隔离；跨校区不能读取、下单、接单或抢单。
- 服务端权威价格、午餐截止、库存预约、重复下单保护、取消释放库存、商家出餐和骑手配送状态机。
- 商家与商品管理接口、订单统计、审计日志和通知发件箱。

## 每日午餐运营流程

1. 管理员先维护商家、菜品模板、取餐点和履约人员；模板本身不会对顾客直接售卖。
2. 每个营业日前，在“午餐运营管理”中选择日期、套餐/菜品、实际售价与当日可售份数，发布当天菜单。顾客端只读取该校区、该日期处于发布状态的餐品；运营台会显示可售、已预约和停售状态。
3. 截止时间前关注订单量和剩余份数；若临时缺货可停止新订单，若要调低份数不得低于已预约数量。付款成功才会将订单交给商家，取消和未支付超时会释放预留份数。
4. 商家按“待接单 → 制作中 → 待取餐”处理；骑手按“抢单 → 已取餐 → 已送达”处理。异常订单通过售后/退款流程闭环，不要靠线下修改库存。

## 上线前必须由运营方提供或完成

1. 正式微信小程序 AppID、合法域名和服务端 HTTPS；将 `touristappid` 替换为正式 AppID。
2. PostgreSQL 生产实例：先备份，再执行 `server/schema.sql`，并为每个校区创建真实档口、餐品、库存和取餐点。
   - 交付命令应使用 `npm --prefix server run migrate`，它会持有数据库迁移锁并记录版本；不要在生产环境手工复制粘贴部分 SQL。
3. 微信登录：服务端已实现 `wx.login` code / OpenID 会话交换；在服务端安全配置 `WECHAT_APPID`、`WECHAT_APPSECRET` 和随机会话密钥策略，生产环境保持 `ALLOW_DEVICE_AUTH=false`。
   - 同时必须配置 `PII_ENCRYPTION_KEY` 与 `IDENTITY_HASH_SECRET`；订单联系人、配送地址和 OpenID 会在服务端加密保存。密钥不得进仓库、客户端、日志或通知载荷。
4. 微信支付：已实现 API v3 JSAPI 下单、客户端调起支付、支付回调验签/解密、超时释放库存，以及已支付取消/商家拒单后的退款队列与退款回调。部署时在服务端配置 `WECHATPAY_*` 变量、私钥路径和平台证书路径；支付成功后才将订单交给商家。严禁写入小程序客户端代码。
5. 消息通知：配置 `NOTIFY_WEBHOOK_URL` 与服务端密钥，接入微信订阅消息或合规短信；用发件箱重试结果做监控。
6. 为商家与骑手建立真实账号和最小权限：用户首次微信登录后，由学校运营端把用户 ID 分配为 `merchant_staff`、`courier_accounts` 或 `platform_admins`；生产环境保持 `ALLOW_LEGACY_OPS_TOKEN=false`。
   - 小程序内已提供“午餐运营管理”页，管理员可维护档口、菜品、骑手和员工授权；首个学校运营管理员仍必须通过受控运维流程写入 `platform_admins`，不要把 `ADMIN_BOOTSTRAP_TOKEN` 放进客户端。
7. 配置监控、告警、数据库备份、日志脱敏、隐私政策、用户协议、退款/售后与配送责任规则。
   - 首次执行加密版 `schema.sql` 前，如已有真实用户或订单数据，须先完成经审批的数据迁移与备份；不要直接对历史明文数据做不可逆批量覆盖。
   - 已提供退出登录和账号注销接口；注销前必须没有进行中的午餐订单。已完成交易只保留加密的必要记录，用于退款、售后、争议处理和法定留存，具体期限须由运营主体在隐私政策中明示。
8. 上线探针：反向代理应只将 `/health` 用于存活检查，将 `/ready` 用于数据库与关键配置就绪检查；探针响应不包含任何密钥或用户数据。
   - 部署前运行 `npm --prefix server run preflight:production`；它只输出缺失项和安全配置问题，不会打印任何密钥。

## 不能仅靠本地构建确认的事项

- 微信支付、订阅消息、真实微信登录和真实骑手调度需要正式平台凭据与测试环境。
- 校区配送范围、费用、营业时间、菜品和库存需要各校区运营人员维护并审核。
